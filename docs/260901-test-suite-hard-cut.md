# Задание: жёсткая урезка тестов

| Поле | Значение |
|------|----------|
| **Статус** | К исполнению |
| **Дата** | 2026-09-01 |
| **Кто** | Только разработчик 1 + сильный ИИ. Разработчик 2 не берёт |
| **Ветка** | `chore/test-suite-hard-cut` от свежего `master` |
| **Связано** | ADR-001; `docs/PROJECT_FOR_TEAM.md` (DoD); `scripts/test_lite.*` |

**Зачем:** сюит ~970 тестов. Полный прогон — десятки минут, поэтому локально крутят `test_lite` и ловят сюрпризы на merge. ИИ дописывает по тесту на каждый assert, на каждый класс CSS и на исходник функции. Два PR, которые оба правят `tests_functional_roles_ui.py` / `tests_issue11_tabs_completion.py`, конфликтуют даже если фичи не пересекаются.

Цель урезки — не «меньше зелёных галочек», а:

1. Стабильный регресс домена и RBAC на годы, без привязки к формулировкам шаблона.
2. Сюит, который гоняется целиком до каждого PR (минуты, не десятки).
3. Мало файлов тестов → меньше merge-конфликтов, пока два разработчика работают параллельно.

## 1. Политика: тест должен заслужить место

Тест остаётся, только если падает при **одном из**:

| Тип | Пример | Зачем |
|-----|--------|--------|
| Инвариант домена | слот не удаляется при −1; ACTIVE только при 100% ready; задача с отчётом не закрывается без approve | Иначе молча ломается деньги/команда/Quality Gate |
| Граница модуля | `profiles` не импортирует `rooms`/`pipeline`; `staffing` не импортирует `pipeline` | ADR-001, будущий вынос |
| RBAC / видимость | фрилансер 403 на каталог и на чужую задачу; вкладки комнаты по роли; директор не создаёт задачу | Конфликт двух фич «все видят» vs «своя роль» |
| Золотой путь | регистрация → wizard → оплата-stub → staffing → invite → ready → задача/отчёт → Hot → inbox | Демо и релиз |
| Запись vs чтение | GET обзора не создаёт слоты; отчёт тимлида ничего не пишет | ИИ легко вставляет side-effect в view |

Всё остальное — удалить, не «сжать».

### Запрещено оставлять и запрещено писать дальше

- `inspect.getsource`, разбор AST **тела** функции, проверка что импорт «внутри функции», «оба порядка импорта в свежем интерпретаторе», `inspect.signature`.
- `test_no_new_migrations_*` — блокирует легитимные миграции и врёт, что схема заморожена.
- Тесты на исчезнувший placeholder, точный CSS-класс, формат таймера `HH:MM:SS`, «ровно 10 событий в ленте», «лейбл кнопки дословно».
- Один сценарий, разрезанный на 8 тестов по одному assert (пакет quick_start / scaling / enterprise / linkedin × отдельно бюджет × отдельно KPI × отдельно HTMX).
- Дубль «сервис вернул 403» **и** «в HTML нет этой же кнопки» **и** «GET чужого директора 403» на каждую роль — оставить **одну** поверхность: сервис для права, HTTP 403 для URL, `assertNotContains` вкладки **один раз** на роль.
- Проверка SQL-строки `WHERE`, числа запросов (`assertNumQueries`), содержимого docstring.
- Тесты админки Django сверх «staff может верифицировать, не-staff не заходит».
- Тесты seed-команд сверх «идемпотентна и создаёт нужную роль».

Исключение по AST: **только** запрет импортов между модулями (как сейчас `profiles/tests_boundaries.py` и `MatchingBoundaryTests.test_staffing_does_not_import_pipeline`). Второй копии проверки `profiles ↛ rooms` не нужно — оставить в одном файле.

## 2. Целевой размер

| Сейчас | Цель | Полный прогон |
|--------|------|----------------|
| ~970 тестов, 28 файлов `tests*.py` | **160–220 тестов, 14–16 файлов** | `python manage.py test` ≤ 2–3 мин на обычной машине разработчика |

После merge `scripts/test_lite.ps1` / `test_lite.sh` **удалить или сделать алиасом полного сюита**. Обход полного прогона — это и был источник конфликтов.

Нельзя: вырезать тесты по одному внутри старых файлов на 1000+ строк. Конфликты останутся, ИИ начнёт «восстанавливать покрытие». Правильный приём — **новые тонкие файлы + удаление старых в одном PR**.

## 4. Что обязательно сохранить (чеклист инвариантов)

Если сценария нет в новом файле — это регресс задания, не «оптимизация».

**BIZ**

- Фрилансер pending до активации; ссылка активации работает.
- `is_available=True` без видео — форма не сохраняет.
- Каталог по умолчанию без неверифицированных и без пустого видео.
- `/freelancers/` — 200 директор/тимлид, 403 фрилансер и менеджер.
- `apps.profiles` не импортирует `rooms`/`pipeline`.

**ROOM / staffing**

- Покупка функции создаёт слот и пытается посадить top-1; пустой пул оставляет слот пустым.
- «Другой сейлер» берёт следующего, №1 не возвращается на этот слот.
- Два `seller_middle` независимы.
- Тимлид в слот не автоназначается и слота не получает.
- Состав правит только директор-владелец в DRAFT/STAFFING.
- Занятый слот нельзя закрыть уменьшением count; БД откатывается (состав, бюджет, слоты).
- Проект становится ACTIVE только когда все фрилансер-слоты `ready`.
- `add_freelancer_to_room` сам по себе не ставит ACTIVE.

**Pipeline**

- Закрыть задачу с `report_required` без approved-отчёта нельзя.
- Фрилансер не квалифицирует в Hot.
- Hot создаёт `MANAGER_HANDOFF` назначенному менеджеру.
- Чужие task/lead URL → 403 фрилансеру.
- Создание задачи — не директор (если в коде уже так; тест фиксирует текущее продуктовое правило).

**Роли на экране**

- Три логина на одном проекте: разные вкладки / блоки Обзора. Это главный конфликт UI двух разработчиков — должен быть **один** файл `tests_room_rbac.py`, а не россыпь по issue11 / overview / tabs / ui.

**Коммуникации**

- Общий чат vs канал директор↔тимлид; фрилансер не видит второй.
- Две разные ссылки Jitsi (комната и dt).

## 5. Как делать (порядок, чтобы не утонуть)

Не рефакторить старые тесты. Переписать сюит.

1. Ветка от `master`. Пока ветка открыта — **не мержить** другие PR с новыми тестами в те же файлы; мелкие фичи пусть подождут или пишут тесты уже по новой политике в комментарии PR (тимлид решает).
2. Добавить в `test_helpers` один хелпер проекта комнаты, если без него каждый новый файл копирует 40 строк setUp. Не строить мини-фреймворк.
3. Создать новые файлы (`tests_staffing.py`, `tests_composition.py`, `tests_room_rbac.py`) с тестами из чеклиста §4. Копировать тела **существующих** рабочих тестов, не писать с нуля «красивее».
4. Наполнить урезанные файлы (matching, chat, sla, teamlead_report, pipeline, users, profiles, core), **удалив** лишние классы пачками, не по одному assert.
5. Удалить файлы из списка §3.
6. `python manage.py test` — зелёный. Если упало — чинить продукт только если инвариант §4 реально сломан; иначе чинить тест.
7. Удалить или выровнять `test_lite.*`. В `PROJECT_FOR_TEAM.md` DoD: полный `manage.py test` обязателен, «тест на каждый partial/CSS» запрещён.
8. Один PR. Описание: было N / стало M, список удалённых файлов, как гонять сюит.

Запрещено в этом PR: менять прод-код «раз уж тесты мешают», расширять matching, трогать шаблоны. Только тесты, хелперы, scripts, абзац DoD.

## 6. Правило на будущее (чтобы сюит не отрос)

В каждый следующий PR:

- Максимум **2 теста на фичу**: 1 сервис (инвариант) + 1 HTTP (доступ или видимость).
- Матрица ролей — `subTest` в **одном** тесте, не 6 методов.
- Новый файл `tests_*.py` — только если это новый bounded context. UI комнаты дописывается в `tests_room_rbac.py`.
- Тимлид режет ревью, если видит `inspect`, `assertContains` длинной русской фразы из макета, или третий тест на тот же POST.

Это и есть предотвращение конфликтов: два разработчика не правят один 1400-строчный `tests_functional_roles_ui.py`.

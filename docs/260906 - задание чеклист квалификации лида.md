# Задание: чеклист квалификации на карточке лида

| Поле | Значение |
|------|----------|
| **Дата** | 2026-09-06 |
| **Ветка** | `feature/lead-discovery-checklist` от актуального `master` |
| **Модуль** | ROOM / pipeline: страница лида. Доска Cold/Warm/Hot и правило «Hot только тимлид» — **не** ломать |
| **Связано** | `LeadQualifyForm`, `set_lead_qualification`; критерии Hot проекта (`input_data.hot_criteria`) |

**Не трогать:** канбан лидов, handoff менеджеру при Hot, `create_lead` (кроме чтения), чат, расторжение, начисления, отчёт тимлида за период.

---

## 1. Зачем

Фрилансер после звонка ставит Cold/Warm «на глаз». Рынок квалифицирует по **готовности купить и качеству контакта**, не по «понравился / не понравился».

На карточке лида нужен чеклист фактов разговора (BANT + следующий шаг). Он **не** двигает колонку сам: Hot по-прежнему только тимлид. Чеклист — доказательства для себя и для тимлида.

---

## 2. Раскладка страницы

`apps/pipeline/templates/pipeline/lead_detail.html`.

Две колонки **напротив друг друга**, не чеклист под историей:

| Слева | Справа |
|-------|--------|
| Общая информация: текущий Cold/Warm/Hot, источник, ФИО, телефон, email, LinkedIn, кто создал, передача менеджеру если Hot | Чеклист + подсказка + «Сохранить чеклист» |

Ниже **на всю ширину**, в таком порядке:

1. Заметки (`notes`) — свободный текст, не вместо галочек.
2. Баннер «Критерии проекта» (`hot_criteria`), как сейчас.
3. Форма тимлида «Квалификация (тимлид)» — без изменений по смыслу (статус + совпавшие критерии Hot + комментарий).
4. История статусов.

На узкой ширине (примерно `< 800px`) колонки **друг под другом**: сначала контакт, сразу чеклист. Не наоборот.

Не использовать `.room-grid` как есть (`auto-fit` / `minmax(260px)`): на широком экране колонки могут стать равными или чеклист уедет вниз. Завести класс, например `.lead-detail-grid`:

```css
.lead-detail-grid {
    display: grid;
    grid-template-columns: minmax(240px, 1fr) minmax(320px, 1.4fr);
    gap: 16px;
    align-items: start;
}
@media (max-width: 800px) {
    .lead-detail-grid { grid-template-columns: 1fr; }
}
```

Левая колонка — `.info-block` без заметок внутри (заметки уезжают вниз). Правая — `.info-block` или `.upload-form` с формой чеклиста.

## 3. Галочки (фиксированные ключи)

Хранить JSON на лиде, например поле `discovery_checks` (`JSONField`, default `dict`). Ключи **стабильные английские**, подписи в шаблоне по-русски. Не свободный список строк.

Группы и ключи — как в продуктовой рамке. Галочка = факт разговора, не оценка «качественный лид».

**Need**
| key | Подпись |
|-----|---------|
| `need_task` | Есть конкретная задача, не «просто смотрю» |
| `need_icp` | Задача похожа на оффер / ЦА этого проекта |

**Authority**
| key | Подпись |
|-----|---------|
| `auth_talked` | Говорили с ЛПР или с тем, кто влияет на решение |
| `auth_signer` | Понятно, кто подпишет (имя или роль) |

**Budget**
| key | Подпись |
|-----|---------|
| `budget_named` | Назвал порядок суммы или что бюджет есть |
| `budget_fit` | Порядок суммы нам подходит (не только «пришлите прайс») |

**Timeline**
| key | Подпись |
|-----|---------|
| `time_has` | Есть срок «нужно к дате / в этом квартале» |
| `time_soon` | Срок близкий, не «когда-нибудь» |

**Диалог (тепло, ещё не сделка)**
| key | Подпись |
|-----|---------|
| `talk_replied` | Был ответ на касание или живой разговор |
| `talk_questions` | Задаёт вопросы / сравнивает / готов слушать |
| `talk_materials` | Запросил материалы, кейс или прайс — без демо/договора |

**Следующий шаг (намерение купить)**
| key | Подпись |
|-----|---------|
| `next_demo` | Просит демо или встречу на конкретные дни |
| `next_proposal` | Просит КП, договор или счёт |
| `next_this_week` | Сказал «давайте на этой неделе» / «нужно внедрить к …» |
| `next_leaning` | Бюджет согласован и склоняется к нам |

В шаблоне — `<fieldset>` + `<legend>` на группу, `checkbox` с `name` ключа. Неотмеченные ключи сохранять как `false` или отсутствующие — при чтении считать отсутствие = нет.

Не добавлять эти 15 галочек на форму **создания** лида (`room_leads`). Сначала контакт, чеклист — на карточке.

## 4. Подсказка (не статус колонки)

После сохранения (и при GET) справа под галочками серый текст, считается **на сервере** из словаря, не JS-единственный источник.

| Условие | Текст подсказки |
|---------|-----------------|
| Нет `talk_*` и нет `need_task` (или почти всё пусто) | «По фактам это Cold: квалификация и прогрев, интереса к сделке ещё нет.» |
| Есть `need_task` и хотя бы один `talk_*`, но нет ни одного `next_*` | «Похоже на Warm: интерес есть, дожмите ЛПР, бюджет и срок.» |
| Есть `need_task` и (`time_has` или `time_soon`) и хотя бы один `next_*` | «Готово отдать тимлиду на Hot: есть потребность, срок и конкретный следующий шаг. Статус Hot ставит только тимлид.» |
| Иначе (частично заполнено) | «Фактов мало для тёплого: отметьте боль или факт диалога.» |

Подсказка **не** пишет `qualification_status`. Не вызывать `set_lead_qualification` из сохранения чеклиста.

Ключ подсказки в context, например `discovery_hint` (`cold` / `warm` / `hot_ready` / `thin`) + готовая русская строка.

---

## 5. Кто видит и кто пишет

| Роль | Чеклист |
|------|---------|
| Фрилансер-создатель этой карточки | видит, отмечает, сохраняет |
| Тимлид проекта | видит те же галочки **и может править** (проверка после звонка / подсказка к Hot) |
| Директор | только чтение (как карточку), без POST |
| Фрилансер чужого лида | по-прежнему 403 на карточку |
| Менеджер с handoff | чтение, без POST чеклиста |

POST, например `pipeline:lead_discovery` (`…/leads/<id>/discovery/`). Guard: создатель-фрилансер **или** `user_can_manage_team`. Остальные — 403.

Архив расторжения: если в проекте уже есть `require_non_archived_room_member` — тот же запрет write, не обходить.

---

## 6. Как хранить и не сломать Hot

- Новое поле на `Lead`, миграция. Не пихать галочки в `contact_info` и не в `matched_hot_criteria`.
- Хелпер списка ключей + подписи + расчёт hint — в `apps/pipeline/` (например `discovery.py`), не в `teamlead_report.py`.
- Сохранение чеклиста не создаёт задачу менеджеру и не меняет `hot_handoff_at`.
- Тест `test_freelancer_cannot_set_or_qualify_a_lead_as_hot` остаётся зелёным: фрилансер может сохранить все `next_*` = true, статус лида как был.

Опционально, не обязательно в этом PR: в форме тимлида подсказка «по чеклисту отмечено: демо, КП…» текстом. Не автозаполнять `matched_hot_criteria` без явного желания — риск тихих расхождений с критериями проекта.

## 7. Как сделать

1. Поле + миграция.
2. `LeadDiscoveryForm`: набор `BooleanField(required=False)` с теми ключами (или один JSON из POST checkbox list).
3. View GET `lead_detail`: отдать форму с initial из `lead.discovery_checks`, hint, флаг `can_edit_discovery`.
4. View POST discovery → redirect на карточку.
5. Шаблон: сетка, fieldsets, кнопка «Сохранить чеклист» только при `can_edit_discovery`.
6. CSS в `static/css/style.css`, не отдельный файл темы.

## 9. Приёмка

Новый файл `apps/pipeline/tests_lead_discovery.py` + не сломать `apps/pipeline/tests.py` (Hot).

1. GET карточки своим фрилансером: две колонки в разметке (класс сетки), слева имя/телефон, справа легенды Need / следующий шаг.
2. POST отмечены `need_task` + `talk_replied`, статус лида не изменился; hint = warm.
3. POST `need_task` + `time_has` + `next_demo` → hint `hot_ready`, `qualification_status` всё ещё не Hot.
4. Фрилансер POST `set_lead_qualification` Hot по-прежнему запрещён.
5. Чужой фрилансер POST discovery → 403.
6. Директор GET видит галочки, POST 403.
7. Тимлид POST discovery 200, значения сохраняются; его форма Hot на странице на месте.
8. `python manage.py test apps.pipeline.tests_lead_discovery apps.pipeline.tests apps.pipeline.tests_kanban`

Ручной чеклист:

- Фрилансер открыл свой лид: слева контакт, справа чеклист, звонок не надо скроллить за историей.
- Отметил боль и диалог → подсказка Warm, колонка на доске как была.
- Отметил next demo → подсказка «отдать тимлиду», колонка не Hot.
- Тимлид на той же карточке видит галочки и ставит Hot своей формой → задача менеджеру как сейчас.
- Узкое окно: контакт сверху, чеклист сразу под ним.

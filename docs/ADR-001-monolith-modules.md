## Контекст

Платформа WowLance объединяет два продукта с точки зрения пользователя:

1. **WOWLANCE BIZ** — биржа / база фрилансеров-сейлов (профили, каталог, регистрация, в т.ч. referral из WOW Talent).
2. **WOWLANCE ROOM** — комната проекта (команда, задачи, отчёты, лиды, материалы; далее чат/видео).

В правках Светланы эти продукты описаны как «микросервисы» с событием оплаты из внешнего конфигуратора (US Closer). В репозитории уже есть рабочий **Django-монолит** с apps `users`, `profiles`, `rooms`, `pipeline`, `core`, демо и тестами.

Команда: стажёры (PM/тимлид + 2× Python + QA), активное использование ИИ. Нужно совместить продуктовую спецификацию правок с реалистичной реализацией и возможностью позже выделить сервисы.

---

## Решение

**Принимаем продуктовую спецификацию правок Светланы (экраны, роли, потоки). Реализацию ведём как единую платформу — modular monolith на Django. Отдельные микросервисы на этапе стажировки / текущего MVP не делаем.**

### Архитектурные границы внутри монолита

| Логический модуль | Django apps | Ответственность |
|-------------------|-------------|-----------------|
| **Identity / BIZ** | `apps.users`, `apps.profiles` | Пользователи, роли, регистрация, профили, каталог, referral, модерация фрилансеров |
| **ROOM** | `apps.rooms`, `apps.pipeline` | Проект, комната, участники, документы, activity; задачи, отчёты, лиды, manager inbox |
| **Shell** | `apps.core` | Лендинг, legal, ролевые дашборды, склейка UI |
| **Payments (внутри монолита)** | новый код в `rooms` или отдельный app `payments` позже | Stub оплаты и/или webhook; внутренний триггер «проект оплачен» → staffing + Room |

`rooms` и `pipeline` в MVP считаются **одним bounded context ROOM** и не разделяются на отдельные сервисы.

### Правила зависимостей

```text
profiles / users  ──X──▶  rooms / pipeline     запрещено
pipeline          ────▶  rooms                 разрешено (фасад доступа к Project/Room)
rooms             ─?─▶  pipeline               только осознанно (метрики); стремиться к фасаду
core              ────▶  users / rooms / …     composition root (UI)
все модули        ────▶  users.User            shared kernel
```

- Бизнес-логику класть в `services.py` (или тонкий `api.py`-фасад модуля), не раздувать views.
- Событие вроде `ProjectPaid` — **внутренний вызов сервиса** в том же процессе (не брокер и не отдельный деплой), пока не доказана необходимость выноса.
- Интеграции (WOW Talent, Stripe): сначала **mock / stub**, контракт рядом с кодом; боевой API — по готовности.

### Стек (без смены платформы)

- Backend/UI: **Django** + server-rendered templates (+ HTMX точечно).
- Не вводим React/SPA и не поднимаем отдельные репозитории сервисов без нового ADR.
- БД на демо может оставаться SQLite; для роста нагрузки планировать PostgreSQL **до** микросервисов.

## Уточнения реализации

Нормативные правила для PR и онбординга. Не меняют решение «монолит», а уточняют, *как* его соблюдать.

### 1. Границы модулей и моделей

**FK `pipeline` → `rooms.Project`**

- ForeignKey у `Task` / `Lead` на `rooms.Project` **допустим** и соответствует правилу `pipeline → rooms`.
- В бизнес-логике `pipeline` проверки доступа, статуса проекта и операций над комнатой **инкапсулировать** через фасад `apps.rooms.services` (например `user_can_access_project`, `user_can_manage_team`), а не дублировать правила ROOM во views/services pipeline.
- Полностью скрывать модель `Project` из queryset’ов pipeline **не требуется**; цель — единые правила доступа ROOM, а не запрет ORM-связи.

**Запрет обратных зависимостей BIZ → ROOM**

- `apps.profiles` (и `apps.users`) **не импортируют** `Project`, `Room`, формы/сервисы `rooms` или `pipeline`.
- Добавление фрилансера в комнату из карточки каталога инициируется **только** представлением в `apps.rooms` (например `rooms:catalog_add_to_room`), куда передаётся идентификатор фрилансера (`freelancer_id`). Каталог в BIZ может содержать ссылку/форму action на этот URL, но не бизнес-логику комнаты.

### 2. Продуктовые интеграции внутри монолита

**WOW Talent (`?ref=wowtalent_...`)**

- Клиент — сервис в BIZ, например `apps.users.wowtalent_client` или `apps.profiles.wowtalent_client`.
- MVP стажировки: **stub/mock** по зафиксированному контракту ответа; переключение на боевой HTTP — смена реализации клиента без ломки вызывающего кода регистрации.

**Событие `ProjectPaid` (US Closer / Stripe)**

- Брокер (RabbitMQ/Kafka и аналоги) **не поднимаем**.
- Единая точка входа: `apps.rooms.services.handle_project_paid(payload)` — перевод проекта в `STAFFING`, создание/инициализация комнаты, запись в `RoomActivity` (и сопутствующие шаги MVP: тимлид/задачи — по продуктовому scope).
- Вызов: внутренний endpoint / webhook Django и/или тестовый wizard оплаты.

**Вкладки комнаты: видео (Jitsi) и чат**

- **Видео (MVP):** генерация ссылки (и при необходимости iframe) на комнату, например `https://meet.jit.si/wowlance-room-<uuid>` или self-hosted Jitsi. Для демо публичный `meet.jit.si` допустим; для боя позже — свой/платный хостинг (приватность, стабильность).
- **Чат (MVP):** без отдельного сокет-кластера. Предпочтительно **HTMX polling** (проще при текущем WSGI/gunicorn). SSE — опционально при переходе на ASGI. WebSocket / отдельный realtime-сервис — phase 2.

## Последствия

### Плюсы

- Пользовательский UX совпадает с правками (BIZ + ROOM как разделы одной платформы).
- Быстрее поставка MVP силами стажёров; меньше инфраструктуры и распределённых сбоев.
- Сохраняется текущий код, демо и тесты.
- Чёткие apps + правило импортов готовят к **будущему** выносу модулей без переписывания продукта.

### Минусы / компромиссы

- Нет независимого деплоя BIZ и ROOM.
- При росте нагрузки масштабируется всё приложение целиком (смягчается БД, кэшем, очередями, CDN — раньше, чем микросервисами).
- Нужна дисциплина границ (иначе снова появятся связи вроде `profiles → rooms`).

### Что сознательно откладывается (не запрещено навсегда)

- Отдельные микросервисы и отдельные БД.
- Обязательный брокер событий между сервисами.
- Вынос только из‑за формулировок «микросервис» в продуктовом документе.

Новый ADR нужен, если: выносим первый сервис; меняем стек UI; вводим обязательную шину событий; режем `rooms` и `pipeline` на разные деплои.

---

## Когда пересматривать решение

Пересмотр в пользу выделения сервиса уместен при сочетании факторов, например:

- устойчивый рост нагрузки / realtime (чат), который бьёт монолит после тюнинга;
- появление отдельной команды на модуль;
- жёсткие требования к изоляции платежей или данных.

До этого приоритет: **модульность внутри монолита** и продуктовый MVP.
